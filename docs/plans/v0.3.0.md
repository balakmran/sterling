# Sterling v0.3.0 — A green build on day one, and one-command fixes

**Status: planned 2026-11-26.** Follows [v0.2.0](v0.2.0.md), released
2026-11-15. The roadmap entry is in [`ROADMAP.md`](../../ROADMAP.md); this
plan is the spec.

## Goal

Lower the wall a brownfield team hits before the gate is useful: adding
Sterling breaks compilation, SpotBugs reports everything at once, the
formatter joins annotations past the column limit, and findings need fixing by
hand one at a time. Then make every failure readable the same way by people,
CI and coding agents.

v0.3.0 is done when a brownfield service can apply Sterling on `LENIENT` and
keep compiling, take a SpotBugs baseline, run `stlFix` to clear what Error
Prone can patch, and reach `STANDARD` with google-java-format's own layout;
and when no Sterling release can merge without the full test matrix having
passed: one cell in CI, the other three locally.

## Verified before planning (2026-11-26)

Checked on a scratch copy of `balakmran/sterling-example-spring-boot`
(Spring Boot 4.1.2, Java 25, Gradle 9.9.1, Lombok, MapStruct, OpenAPI
generator), with Sterling 0.2.0 from the Plugin Portal and a local copy of
Sterling with `formatAnnotations()` removed (`--include-build`). A class was
added with this field, in google-java-format's layout:

```java
@NotBlank(message = "uadInput is required and must not be blank")
@Size(max = MAX_PAYLOAD_SIZE, message = "uadInput exceeds maximum allowed size (10 MB)")
@Deprecated
private String uadInput = "";
```

| Question | Result |
|---|---|
| Does 0.2.0 join stacked Bean Validation annotations? | Yes. `stlFmt` joined `@NotBlank(...) @Size(...)` into one 156-column line, left `@Deprecated` on its own, and `stlFmtCheck` passed. It also joined `@Nullable` onto field and method declarations (`@Nullable public String getNote() {`) |
| Does google-java-format alone undo it? | Yes. With `formatAnnotations()` removed, `stlFmtCheck` fails on 0.2.0's output and `stlFmt` restores one annotation per line, with no line over 100 columns. A second run changes nothing |
| What does google-java-format alone do with a single field annotation? | It puts it on the field's line: `@Nullable private String note;` (style guide §4.8.5.4 allows this). Method annotations go one per line (§4.8.5.3) |
| Does Error Prone's `AnnotationPosition` read `@Target`? | Yes. Turned on as an error, it flagged `@Nullable` (JSpecify, `TYPE_USE` only) before `private` and before `public`: "is a TYPE_USE annotation, so should appear after modifiers and directly before the type" |
| What does it do with Jakarta constraints? | Nothing. `@NotBlank` and `@Size` target `TYPE_USE` and `FIELD`, `METHOD`, `PARAMETER`, `CONSTRUCTOR`, `ANNOTATION_TYPE` (jakarta.validation-api 3.1.1), and the check treats them as declaration annotations. `List<@NotBlank String>` was left alone too |
| Is `AnnotationPosition` on by default? | No: it is in Error Prone 2.52.0's disabled set (`BuiltInCheckerSuppliers.DISABLED_CHECKS`) |
| Does patching work in a Lombok and MapStruct build? | Yes. `-XepPatchChecks:AnnotationPosition -XepPatchLocation:IN_PLACE` rewrote the two declarations to `private @Nullable String note;` and `public @Nullable String getNote()`, with stray whitespace that `stlFmt` then removed. Lombok's `@Value @Builder` class was untouched and the build passed |
| Does `-XepAllErrorsAsWarnings` demote NullAway, which Sterling sets to `ERROR` explicitly? | Yes. A `DeadException` and a NullAway dereference in a `@NullMarked` package both became warnings and `compileJava` succeeded |
| Does `AddNullMarkedToPackageInfo` mark packages? | Only partly. It reports an existing `package-info.java` without `@NullMarked` ("Apply @NullMarked to this package"), and nothing for a package with no `package-info.java`. With `-XepPatchChecks` it produced no change, in place or as a patch file. Cause not found |
| Does the SpotBugs Gradle plugin expose a baseline? | Yes: `getBaselineFile()`, a `RegularFileProperty`, on both `SpotBugsExtension` and `SpotBugsTask` (6.5.13) |
| Is the Problems API stable? | Still `@Incubating` in Gradle 9.9.1, as in 9.0.0. `ProblemReporter` and `ProblemSpec` have the same methods in both |
| Does Gradle already report javac's findings as problems? | Yes. A failing `DeadException` appeared in `build/reports/problems/problems-report.html` with its message and suggested fix, with nothing from Sterling |

## Decisions

| Decision | Choice | Notes |
|---|---|---|
| `formatAnnotations()` | Off by default in every profile; `format.formatAnnotations = true` turns it on | google-java-format is the Google Java Style Guide's formatter and keeps to its 100-column limit (§4.4). Spotless's step picks type-use annotations from about 700 simple names rather than `@Target` (§4.8.5.1), and joined 156-column lines the gate accepted |
| Type-use placement (§4.8.5.1) | Error Prone's `AnnotationPosition`, patched by `stlFix`, enforced only if the project turns it on | It reads `@Target`, as the guide defines a type-use annotation. It treats annotations that are both type-use and declaration (Jakarta's constraints) as declaration annotations, which matches google-java-format's one-per-line layout |
| Upgrade from 0.2.0 | One `stlFmt` commit, though google-java-format is still 2.0.0 | Files where 0.2.0 joined annotations fail `stlFmtCheck` until reformatted. `upgrade-sterling` decides on the reformat commit from `stlFmtCheck`, not from the formatter's version |
| `LENIENT` and compile errors | `errorProne.errorsAsWarnings`, convention true in `LENIENT`, false otherwise; adds `-XepAllErrorsAsWarnings` | Applies to NullAway too (verified). `LENIENT` means nothing new fails `build`; a team marking packages `@NullMarked` while on `LENIENT` sees warnings, and `STANDARD` turns them back into errors |
| `errorsAsWarnings` with `warningsAsErrors` | Rejected together, with a message naming both | `-Werror` would turn the demoted errors back into failures, so the pair means nothing |
| javac's warning cap | Raise `-Xmaxwarns` while `errorsAsWarnings` is on | javac stops printing after 100 warnings by default (check), which would hide most of a brownfield codebase's findings |
| SpotBugs baseline | `spotbugs.baselineFile`, a convention on the SpotBugs extension's `baselineFile`, so the project's own setting wins | Same pattern as `effort` and `reportLevel`. Unset by default |
| Generating the baseline | Documented: run `spotbugsMain --continue`, copy `build/reports/spotbugs/main.xml` to `config/spotbugs/baseline.xml` | A task that writes into the repository is a change task; two commands don't need one (rule 1) |
| `stlFix` mechanism | When `stlFix` is in the task graph, the project's own `compileJava` and `compileTestJava` run with `-XepPatchChecks:<list> -XepPatchLocation:IN_PLACE`, never up to date and never cached; then `stlFmt` | A separate `JavaCompile` per source set would have to copy every setting of the real one, including the project's own; it can't be complete. The patch arguments are compiler arguments, so they're part of the cache key and normal builds never reuse a patching run's outputs |
| `stlFix` and verification | `stlFix` with any verify task in the same build fails fast | Plugin authoring rule 8: change or verify, never both |
| Which checks `stlFix` patches | `errorProne.patchChecks`, a set; default: `AnnotationPosition` plus a list of default-on checks whose fixes keep behaviour, chosen during implementation from Error Prone 2.53.0's docs and dogfooding | Not every suggested fix preserves behaviour (removing an unused variable can drop a side effect) |
| Patching and `errorProne.enabled = false` | `stlFix` skips the compile pass and runs `stlFmt` only | Nothing to patch with |
| JSpecify | Added to every source set's compile-only configuration, through `sourceSets.configureEach`, while NullAway is active | NullAway runs on every `JavaCompile`, but 0.2.0 adds JSpecify to `compileOnly` and `testCompileOnly` only, so a `@NullMarked` package in an `integrationTest` suite or test fixtures needs the annotations from elsewhere (Spring brings them; a plain library doesn't). From the code, not reproduced: the example service has Spring |
| Console format | Version 1: `<path>[:<line>] [<Tool>:<Rule>] <message>`, path relative to the root project with `/`. Covers SpotBugs and JaCoCo lines; javac's lines are documented alongside | 0.2.0's coverage lines print `com/example/Foo.java`; version 1 prints the real source path (`src/main/java/com/example/Foo.java`) so matchers and IDEs can link it. `stlInfo --json` gains `consoleFormat: 1` |
| Pull request annotations | A GitHub Actions problem matcher, `docs/guide/sterling-problem-matcher.json`, matching javac's lines and format version 1 | Works on private repositories without code scanning. SARIF upload is the second recipe, for SpotBugs, where code scanning is available |
| Problems API | Reports SpotBugs findings (with file and line) and coverage shortfalls, from the summary tasks, in one class; a `LinkageError` falls back to the console only | The API is incubating but unchanged from 9.0.0 to 9.9.1. Gradle already reports javac's diagnostics. No IDE integration is promised |
| Null-safety progress | `stlInfo` counts main packages (directories of non-generated main sources) and those whose `package-info.java` carries `@NullMarked` | Text: `NullAway: on (...; 3 of 7 main packages @NullMarked)`. JSON: `nullAway.packages: {"total": 7, "nullMarked": 3}`. Classes marked one by one aren't counted |
| Test matrix | CI runs one cell, 9.0.0 × 25, on every pull request, as today. The other three run locally with `functionalTestLocal`, before a change is done and before a release PR merges | Saves Actions time and keeps PRs fast. `ci.yml` keeps its comment on how to restore all four |
| Auto-release | The `auto-release` job in `release.yml` is removed: a release PR, dependency-only or not, waits for the maintainer to run the release checklist and merge | In the automated path nobody ran `functionalTestLocal`, so patches reached the Plugin Portal tested on one cell. Dependabot's own PRs keep auto-merging: the full matrix runs once, on the release |
| Cooldown | Dependabot `cooldown` on the Gradle ecosystem for consumer tools, 7 days (check the option's syntax) | A plugin release published today would otherwise reach consumers' buildscript classpath with no person involved |
| Provenance | `actions/attest-build-provenance` on the jars `publishPlugins` uploads | Sterling's own release; not the consumer SBOM or `provenance.json` features v0.1.0 lists as not planned |
| Latest JDK and next Gradle | A local run before each release, on the checklist: `functionalTest -Psterling.test.java=27`, and `-Psterling.test.gradle=<newest release candidate or nightly>` | No scheduled workflow, so no Actions time. A failure is reported, not a release blocker, unless it's a regression in a supported cell |

## Configuration model

### DSL additions

```kotlin
sterling {
    format {
        formatAnnotations = false           // default; true adds Spotless's formatAnnotations()
    }
    errorProne {
        errorsAsWarnings = false            // default from profile: true in LENIENT
        patchChecks.add("MissingOverride")  // stlFix's list; default: Sterling's
    }
    spotbugs {
        baselineFile = file("config/spotbugs/baseline.xml") // unset by default
    }
}
```

| Setting | Type | Default |
|---|---|---|
| `format.formatAnnotations` | `Property<Boolean>` | false |
| `errorProne.errorsAsWarnings` | `Property<Boolean>` | From the profile |
| `errorProne.patchChecks` | `SetProperty<String>` | Sterling's list (see Decisions) |
| `spotbugs.baselineFile` | `RegularFileProperty` | Unset |

Profile table change: `errorProne.errorsAsWarnings` is true in `LENIENT`,
false in `STANDARD` and `STRICT`.

### Validation

- `errorsAsWarnings` and `warningsAsErrors` both true fails when the compile
  arguments are resolved, naming both settings.
- `stlFix` in the same build as `stlCheck`, `stlLint`, `stlSec`, `stlCov`,
  `stlFmtCheck` or `check` fails at task-graph time, naming the conflict.
- A `baselineFile` that doesn't exist fails `spotbugsMain` with SpotBugs's
  own message (no Sterling check).

## Behaviour spec

### Formatting

- `Formatting.java` calls `java.formatAnnotations()` only when
  `format.formatAnnotations` is true, read inside the same `spotless { java
  { } }` action as `style` and `ratchetFrom`, with `finalizeValueOnRead()`.
- The duplicate-step message names only `googleJavaFormat()` while the step
  is off; a project's own `formatAnnotations()` then works and is no longer a
  clash.
- `stlInfo`: `Formatting: on (google-java-format 2.0.0 via Spotless 8.12.0)`,
  with `; formatAnnotations on` only when on. JSON:
  `format.formatAnnotations`.
- `docs/guide/tools.md` "Formatting" says Sterling formats as
  google-java-format does, cites the guide's §4.8.5, and shows how to get
  §4.8.5.1 placement with `stlFix` and enforce it with `AnnotationPosition`.

### Error Prone in `LENIENT`

- A `CommandLineArgumentProvider` with an `@Input` (as `WarningsAsErrors`
  does) adds `-XepAllErrorsAsWarnings` and a raised `-Xmaxwarns` while
  `errorsAsWarnings` is on and Error Prone is enabled.
- `stlInfo`: `Error Prone: on (2.53.0; errors are warnings)`. JSON:
  `errorProne.errorsAsWarnings`.
- `docs/guide/adopting.md` step 1 drops "except Error Prone's error-level
  findings".

### SpotBugs baseline

- `spotbugs.baselineFile` becomes a convention on the SpotBugs extension's
  `baselineFile`.
- `stlInfo`: `SpotBugs: on (...; baseline config/spotbugs/baseline.xml)`.
  JSON: `spotbugs.baselineFile` (relative path or `null`).
- `stlSecSummary` prints only findings SpotBugs reported, so baselined ones
  stay out of the console (check that the XML report leaves them out).

### JSpecify on every source set

`NullAway.addDependencies` adds `org.jspecify:jspecify` to
`sourceSet.getCompileOnlyConfigurationName()` for every source set, in
`withDependencies { }` as today, instead of the fixed `compileOnly` and
`testCompileOnly`. `VersionOverrides` still reads the override from
`compileOnly`.

### `stlFix`

- Registered in group `sterling`, description "Applies Error Prone's fixes
  to the sources, then formats them. Changes code."
- Depends on `compileJava` and `compileTestJava` (every `JavaCompile` of a
  main or test source set), then `stlFmt`, which `mustRunAfter` them.
- In `taskGraph.whenReady`, when the graph holds `stlFix`, each of those
  compile tasks gets, through a `CommandLineArgumentProvider` with `@Input`
  values, `-XepPatchChecks:<patchChecks>` and `-XepPatchLocation:IN_PLACE`,
  and `outputs.upToDateWhen { false }` and `outputs.doNotCacheIf(...)`.
- Each check in `patchChecks` is also enabled at `WARNING` for that run, in
  case patching needs the check on (open question 1).
- Sources under `build/generated` are already out of Error Prone's reach
  (`excludedPaths`), so they're never patched.
- The compile pass doesn't fail on findings it can't patch; the report says
  to run `stlLint` afterwards.

### Console format 1

- `stlSecSummary`: unchanged.
- `stlCovSummary`: each line names the source file under main's source
  directories: `src/main/java/com/example/Foo.java [JaCoCo:INSTRUCTION] 12 of
  40 missed`. A class with no source file found falls back to the package
  path, as in 0.2.0.
- `docs/guide/tools.md` gains "Reading Sterling's output": format 1, javac's
  line format, and that changing either format bumps `consoleFormat`.
- `docs/guide/sterling-problem-matcher.json`: two patterns, javac's
  `path:line: (error|warning): [Check] message` and format 1.

### Problems API

- One package-private class reports through the injected `Problems`
  service: a problem per SpotBugs finding (`ProblemId` in a `sterling`
  group, the pattern as its name, file and line, severity from SpotBugs's
  rank) and one per coverage shortfall.
- Called from `stlSecSummary` and `stlCovSummary`; the console lines are
  printed either way.
- A `LinkageError` from the API is caught once and logged at info level, so
  a change in an incubating API can't fail a build.

### `stlInfo` null-safety progress

- Inputs: main's `java` source directories outside `build/generated`, as a
  `FileCollection` wired at configuration time.
- At execution: every directory with a `.java` file is a package; it's
  `@NullMarked` when its `package-info.java` has `@NullMarked` or
  `@org.jspecify.annotations.NullMarked` on the package declaration.
- Without `java`, or with NullAway inactive, the count is left out.
