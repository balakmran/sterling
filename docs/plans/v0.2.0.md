# Sterling v0.2.0 — Adopt it on a real Spring Boot 4 service

**Status: released 2026-11-15.** [v0.2.0](https://github.com/balakmran/sterling/releases/tag/v0.2.0) is on the Gradle Plugin Portal. Still open: the Dependabot patch-release path has not run on a real bump, and the agent plugin's remaining evals (see its plan). Originally planned 2026-11-14. Follows [v0.1.0](v0.1.0.md), released
2026-11-14. The agent plugin that ships in this release has its own plan,
[`agent-plugin.md`](agent-plugin.md); this plan covers the Gradle plugin, the
docs, the example service and the release automation, and fits the agent
plugin's steps into one order.

## Goal

Remove the reasons a Spring team backs out in the first hour: a reformat that
touches every file, coverage dragged down by code nobody wrote, integration
tests that don't count, NullAway noise from Spring's own patterns, and
failures that only say "see the report".

v0.2.0 is done when a Spring Boot 4 service with Lombok, generated OpenAPI
code and an integration test suite adopts Sterling with nothing in its build
but the plugin, a profile and a coverage exclude or two, and when that
service is public, as proof that closed-source adopters can't give.

## Scope

### In

- **Spring-aware NullAway defaults:** contract checking, test assertion
  libraries, and documentation of NullAway's known limits with Spring
- **Spring Boot reaction:** with `org.springframework.boot` applied, the
  application's main class is left out of coverage
- **Lombok:** a functional test and an accurate docs section
- **Formatting:** `format.style` (`GOOGLE`, `AOSP`) and `format.ratchetFrom`
- **Coverage:** every `Test` task counts by default, narrowed with
  `coverage.testTasks`; classes compiled from generated sources are left out
- **Supported tool version overrides** for Error Prone, NullAway, JSpecify,
  SpotBugs and JaCoCo, shown in `stlInfo`
- **Console summaries** when `stlSec` or `stlCov` fails
- **`stlInfo --json`** (specified in [`agent-plugin.md`](agent-plugin.md))
- **Multi-module recipe:** a `build-logic` convention plugin, documented and
  covered by a functional test
- **Docs:** a migration page (from Spring's NullAway snippet, from a
  hand-written `build-logic`) and per-release upgrade notes
- **Example service:** a public Spring Boot 4 service built with Sterling
- **Release automation:** Dependabot bumps that change no findings become
  patch releases without manual steps
- **The agent plugin** (`agent-plugins/sterling/`), per its plan

## Decisions

| Decision | Choice | Notes |
|---|---|---|
| `CustomContractAnnotations=org.springframework.lang.Contract` | **Not set** | The roadmap named it first, but NullAway accepts any annotation whose simple name is `Contract` since 0.12.11 (`ContractUtils.hasSimpleNameContract`; changelog "Accept any annotation with simple name `Contract`", #1295). Setting it is redundant. A functional test proves Spring's `@Contract` (on `org.springframework.util.Assert`) is honoured without it |
| `NullAway:CheckContracts` | `true` in every profile | `io.spring.nullability` sets it. Checks that a method's body matches a `@Contract` ending in `!null` (NullAway doesn't verify `-> fail`); reports only in `@NullMarked` code. Can add findings, which is why this is a minor release |
| `NullAway:HandleTestAssertionLibraries` | `true` on every `JavaCompile` | `io.spring.nullability` sets it for tests. AssertJ's and JUnit's assertions then count as null checks. It only affects calls to those libraries, so main code is unaffected; one setting for every task keeps it simple |
| Spring's AssertJ contract annotation | Nothing to add | Same simple-name rule covers `org.assertj.core.internal.annotation.Contract` |
| `JSpecifyMode` | Unchanged: `STRICT` only | Spring's plugin turns it on; Spring's docs call it "still under development" and a second step. Sterling keeps the v0.1 decision |
| Spring support placement | In the main plugin. Contract settings apply everywhere (harmless without Spring); the main-class exclusion reacts to `org.springframework.boot` | `ROADMAP.md` rule 6 |
| Application class out of coverage | Automatic when `org.springframework.boot` is applied, from `resolveMainClassName`'s output; no setting | Every Boot service needs it today (`README.md` tells them to add an exclude). Add a setting only if dogfooding asks for one |
| Classes from generated sources | Always left out of coverage, like SpotBugs already does | JaCoCo has no source-path filter, and `javax`/`jakarta` `@Generated` are source-retention, so MapStruct and OpenAPI output count today. No setting, matching SpotBugs |
| Which `Test` tasks count | Every `Test` task in the project by default; `coverage.testTasks` narrows it | The "done when" service has `integrationTest` and must need no coverage setting. JVM test suites are `Test` tasks, so they're included |
| `format.style` | `GOOGLE` (default) or `AOSP`, through Spotless's `googleJavaFormat(v).aosp()` | Same pinned engine with 4-space indentation, for a far smaller reformat |
| `format.ratchetFrom` | Unset by default; a git ref such as `origin/main` | Spotless's ratchet. A moved ref is honoured whether Gradle invalidates the configuration cache (it tracks the ref's file) or reuses the entry; the functional tests check it |
| Reading `style` and `ratchetFrom` | Inside Sterling's `spotless { java { } }` action, which Spotless runs when `spotlessJava` is configured; both properties `finalizeValueOnRead()` | Spotless has no lazy step API. It runs the action in `afterEvaluate`, or when `spotlessJava` is realised if that's later, so the `sterling { }` block is always seen. If a build realises `spotlessJava` early and sets a value after Spotless's `afterEvaluate`, the `set` fails with Gradle's "final" error instead of being ignored silently |
| Tool version overrides | Supported and tested for Error Prone, NullAway, JSpecify (a declared dependency), SpotBugs (`spotbugs { toolVersion }`) and JaCoCo (`jacoco { toolVersion }`). `stlInfo` shows "project override" | They already worked in 0.1 as a side effect; 0.2 makes them a promise. google-java-format is not overridable (Out) |
| Console summaries | Finalizer tasks that read the XML reports and print `path:line [Tool:Rule] message`, the format 0.3.0 will use everywhere | The roadmap moved this into 0.2: "Open the HTML report" is a first-hour reason to back out, and agents can't read HTML |
| Generated-class list | One internal task, `stlGeneratedClasses`, used by both the SpotBugs filter and coverage | Replaces the scan inside `stlSpotbugsFilter`, so both tools agree on what's generated |
| Example service | A new public repository, `balakmran/sterling-example-spring-boot` | Separate from this repo so it builds Sterling from the Plugin Portal, as users do |
| Patch releases from Dependabot | Auto-merge of non-finding bumps once CI passes; release-please and its release PR run with a GitHub App token; the release PR auto-merges when every commit since the last tag is a `fix(deps)` | See "CI and release" |
| Agent plugin version | Same as Sterling's; first ships in 0.2.0 | [`agent-plugin.md`](agent-plugin.md) |

## Configuration model

### DSL additions

```kotlin
import dev.balakmran.sterling.FormatSettings

sterling {
    format {
        style = FormatSettings.Style.AOSP   // GOOGLE (default) | AOSP
        ratchetFrom = "origin/main"         // unset by default
    }
    coverage {
        testTasks = setOf("test", "integrationTest") // default: every Test task
    }
}
```

| Setting | Type | Default (every profile) |
|---|---|---|
| `format.style` | `Property<FormatSettings.Style>` | `GOOGLE` |
| `format.ratchetFrom` | `Property<String>` | unset |
| `coverage.testTasks` | `SetProperty<String>` | unset, meaning every `Test` task |

No profile changes these. `Profile`'s defaults table is unchanged except that
the docs gain the new rows.

### Validation

- `coverage.testTasks` naming a task that doesn't exist or isn't a `Test`
  fails when the coverage settings are applied (`taskGraph.whenReady`) with
  the allowed names listed.
- An empty `ratchetFrom` string is rejected; to turn ratchet off, leave it
  unset.

## Behaviour spec

### NullAway

On every `JavaCompile`, while NullAway is active, the options become:

| Option | Value | Since |
|---|---|---|
| `NullAway:OnlyNullMarked` | `true` | 0.1 |
| `NullAway:JSpecifyMode` | `true` when `nullAway.jspecifyMode` | 0.1 |
| `NullAway:CheckContracts` | `true` | 0.2 |
| `NullAway:HandleTestAssertionLibraries` | `true` | 0.2 |

- Same mechanism as 0.1: `NullAway.options(...)` returns the map, added with
  `putAll(provider)`, empty while NullAway is off.
- A project's own `options.errorprone.option(...)` for any of these still wins
  (Error Prone takes the last value on the command line; a functional test
  checks the direction).
- `docs/guide/tools.md` gains "NullAway with Spring": the options above, that
  any `@Contract` annotation is honoured, JSpecify mode's JDK requirement (JDK
  22+, or `-XDaddTypeAnnotationsToSymbol=true` on 21.0.8+, which
  `net.ltgt.errorprone` adds; some vendors' JDK 21 builds lack it), and the
  limits Spring's
  [null-safety page](https://docs.spring.io/spring-framework/reference/core/null-safety.html)
  lists (generic type variables, arrays outside JSpecify mode, dataflow,
  lambdas, `InitializingBean`-style late init with
  `@SuppressWarnings("NullAway.Init")`, reflection, map keys, overrides
  without nullness), each with the suppression Spring documents.

### Generated classes

New internal task **`stlGeneratedClasses`** (`dev.balakmran.sterling.internal`,
`group` none, a description):

- Inputs: main's `java` source directories under `build/generated`, plus
  javac's annotation-processor output directory (the same set
  `stlSpotbugsFilter` scans in 0.1).
- Output: `build/sterling/generated-classes.txt`, one binary class name per
  line (`com.example.api.OrderDto`).
- `stlSpotbugsFilter` reads this file instead of scanning; its output is
  unchanged.
- Cacheable; depends on `compileJava` (annotation-processor output exists only
  after it).

### Coverage

1. **Test tasks.** The tasks counted are `coverage.testTasks`, or every `Test`
   task when it's unset. In `taskGraph.whenReady`, as in 0.1:
   - every counted `Test` task's JaCoCo agent follows `coverage.enabled`;
     other `Test` tasks get no agent while coverage is on
   - `jacocoTestReport` and `jacocoTestCoverageVerification` get
     `executionData` from every counted task
2. **Wiring.** Both JaCoCo tasks `dependsOn` every counted task (replacing
   `dependsOn("test")`), and each counted task is `finalizedBy` the report
   when coverage is on, through `Flags.whenOn`. The task list is a provider
   over `tasks.withType(Test)`, so a suite registered after Sterling is
   included.
3. **Class directories.** Main's classes, minus:
   - `coverage.excludes` (0.1)
   - every class in `generated-classes.txt`, with its nested classes
     (`Name.class`, `Name$*.class`)
   - with `org.springframework.boot` applied: the class named in
     `resolveMainClassName`'s output file, with its nested classes
4. **Laziness.** The two lists are only known at execution, so the exclusion
   is a `Spec<FileTreeElement>` implemented as a small static class holding
   the two `File`s, read when JaCoCo walks the class directories. Both files
   are declared inputs of the report and the verification, so a change to
   either reruns them. No lambda captures `Project` or the extension.
5. **Spring Boot.** `pluginManager.withPlugin("org.springframework.boot")`
   adds the dependency on `resolveMainClassName` and its output file; without
   the Boot plugin nothing about it is registered.
6. `README.md` drops the "leave the application class out" snippet;
   `docs/guide/tools.md` says what's left out automatically and why.

### Formatting

- `format.style`: Sterling's `java { }` action calls
  `googleJavaFormat(pin)` and, when the style is `AOSP`, `.aosp()` on the
  returned config.
- `format.ratchetFrom`: when set, Sterling calls `ratchetFrom(ref)` on its
  `java { }` format (not on `spotless { }`, so a project's other formats keep
  their own setting).
- Both are read inside the action and `finalizeValueOnRead()` (see Decisions).
- Ratchet needs the ref locally. A shallow CI checkout fails with Spotless's
  "No such reference" error. `docs/guide/adopting.md` says to use
  `fetch-depth: 0` or `git fetch origin main` first, and that ratchet
  compares with the merge base, not the ref itself.
- `adopting.md`'s reformat section offers three ways in: reformat once
  (default), `AOSP` for a 4-space codebase, or `ratchetFrom` to format only
  what changes.
- `stlInfo` shows `google-java-format 2.0.0, AOSP style, ratchet from
  origin/main via Spotless 8.11.0` (style and ratchet only when not default).

### Tool version overrides

| Tool | How a project overrides it | What `stlInfo` shows |
|---|---|---|
| Error Prone | `errorprone("com.google.errorprone:error_prone_core:<v>")` | `<v> (project override)` |
| NullAway | `errorprone("com.uber.nullaway:nullaway:<v>")` | same |
| JSpecify | `compileOnly("org.jspecify:jspecify:<v>")` | same |
| SpotBugs | `spotbugs { toolVersion = "<v>" }` | same |
| JaCoCo | `jacoco { toolVersion = "<v>" }` | same |

- Dependency-based overrides are read from the declared (not resolved)
  dependencies of the configuration, through a provider wired at
  configuration time; nothing is resolved by `stlInfo`.
- SpotBugs and JaCoCo compare the extension's value with Sterling's pin.
- `stlInfo --json` adds `"versionSource": "sterling" | "project"` beside each
  tool's `version` (schema version stays 1: an added key).
- `docs/guide/tools.md` documents each override and says it's supported; the
  release notes for a Sterling bump of that tool say to drop the override.

### Console summaries

- **`stlSecSummary`** (internal, finalizes `spotbugsMain`, runs only when
  SpotBugs is on and the XML report exists): prints each finding as
  `src/main/java/com/example/Foo.java:42 [SpotBugs:NP_NULL_ON_SOME_PATH] <short message>`
  at error level, at most 50, then `... and N more: build/reports/spotbugs/main.html`.
  Source paths come from the report's `SourceLine` and main's source
  directories.
- **`stlCovSummary`** (internal, finalizes `jacocoTestCoverageVerification`
  when coverage is on): prints the measured instruction and branch coverage
  against the thresholds, then the ten classes with the most missed
  instructions, each as `com/example/Foo.java [JaCoCo:INSTRUCTION] 12 of 40 missed`.
  Prints only when the verification failed: the verification's first action
  writes `build/sterling/coverage-verification-failed` and its last action,
  which runs only on success, deletes it; the summary prints while the marker
  is there and consumes it (open question 2).
- Both are `@UntrackedTask`, configuration-cache safe, and read the report as
  an `@InputFile`. Neither loads external DTDs or entities. SpotBugs' report
  is parsed with document type declarations rejected, as `stlSpotbugsFilter`
  does; JaCoCo's reports declare one (`report.dtd`), so it's allowed there but
  never fetched.
- Neither changes a task outcome: `spotbugsMain` and the verification still
  fail as before.

### `stlInfo`

- Text form gains the style, ratchet, test tasks and "project override"
  details above. Example:

  ```
  Formatting:           on   (google-java-format 2.0.0, AOSP style via Spotless 8.11.0)
  Error Prone:          on   (2.53.0 (project override); warnings are not errors)
  Coverage:             on   (JaCoCo 0.8.16; instruction >= 80%, branch >= 70%; test, integrationTest; Spring Boot main class excluded)
  ```

- `--json` as specified in [`agent-plugin.md`](agent-plugin.md#stlinfo---json-gradle-plugin),
  with `format.style`, `format.ratchetFrom` (or `null`),
  `coverage.testTasks` (the resolved names), `coverage.excludesMainClass`
  (boolean) and each tool's `versionSource`.

### Multi-module recipe

`README.md`'s "Multi-module builds" and a new section in
`docs/guide/adopting.md`:

```kotlin
// build-logic/build.gradle.kts
plugins { `kotlin-dsl` }
dependencies { implementation("dev.balakmran.sterling:sterling-gradle-plugin:0.2.0") }

// build-logic/src/main/kotlin/java-conventions.gradle.kts
plugins {
    java
    id("dev.balakmran.sterling")
}
java { toolchain { languageVersion = JavaLanguageVersion.of(25) } }
```

- Each module applies `id("java-conventions")`, and may add its own
  `sterling { }` (a per-module coverage threshold, for example), which wins
  over anything the convention plugin sets as a convention.
- `./gradlew stlCheck` at the root runs every module's gate; `stlInfo` prints
  one block per module.
- The `build-logic` dependency on Sterling is how the version is pinned once.

### Example service

`balakmran/sterling-example-spring-boot`, public, Apache-2.0:

- Spring Boot 4.1, Java 25, Gradle 9.x wrapper, `gradle-daemon-jvm.properties`.
- A small REST service with a JPA-free domain (no database needed in CI),
  Lombok `@Builder`/`@Value` types, a MapStruct mapper, and an OpenAPI-
  generated API interface (`org.openapi.generator`) under `build/generated`.

- CI: `./gradlew build` and `-Psterling.profile=strict`, plus a ratchet job
  with `fetch-depth: 0`.
- Its README links back here and shows `stlInfo` output.
- Built against an unreleased Sterling with `--include-build` while 0.2.0 is
  in progress; switched to the Plugin Portal version once released.

## CI and release

- **CI** unchanged (one cell on PRs; `functionalTestLocal` for the other
  three), plus the agent plugin's job (see its plan).
- **Dependabot** (`.github/dependabot.yml`):
  - Gradle updates with `commit-message.prefix: "fix"` and
    `include: "scope"`, giving `fix(deps):`; GitHub Actions with `ci`.
  - Weekly, grouped: one PR for build-only tools, one per consumer tool.
- **Auto-merge** (`dependabot-automerge.yml`, on `pull_request_target` for
  Dependabot only): `dependabot/fetch-metadata` reads the dependency names.
  - Build-only tools, JSpecify, JaCoCo, the Gradle plugins of Spotless,
    SpotBugs and Error Prone, and actions: `gh pr merge --auto --rebase`.
    These change no findings (`ROADMAP.md` rule 7).
  - `error_prone_core`, `nullaway`, `spotbugs`, `google-java-format`: label
    `changes-findings`, no auto-merge. The maintainer rewrites the commit as
    `feat(deps): ...` with a note on what may newly fail, and adds the
    `upgrading.md` entry. Dependabot can't set a prefix per dependency, which
    is why these need the hand edit.
  - Needs "Allow auto-merge" in repository settings and the required checks.
- **release-please with a GitHub App token.** The App from the agent plugin
  plan is installed on `balakmran/sterling` too, with `contents: write` and
  `pull-requests: write`. A release PR opened with its token starts CI, so
  the "approve the run" step in `CLAUDE.md` goes away (update `CLAUDE.md`).
