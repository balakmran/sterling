# Sterling v0.1.0 — First release

## Goal

Ship a usable quality gate for Java 21+ projects: formatting, compile-time
analysis (including nullness), bytecode analysis and coverage, each one
switchable by the consumer, with defaults driven by a single `profile`.

v0.1.0 is done when someone can add one line to a Java 25 Spring Boot 4
service's `build.gradle.kts`, run `./gradlew build`, and have Sterling
format-check, Error Prone- and NullAway-check, SpotBugs-check and
coverage-verify it, with the plugin resolved from the Gradle Plugin Portal.

## Scope

### In

- Two plugin IDs: `dev.balakmran.sterling` (base) and
  `dev.balakmran.sterling.java`
- The `sterling { }` extension: `profile` and `attachToCheck`, plus `format`,
  `errorProne`, `nullAway`, `spotbugs` and `coverage` blocks, each with an
  `enabled` flag
- A small set of per-tool settings (see the DSL below), and documented, tested
  access to each tool's own configuration for everything else
- The profile settable from the `sterling.profile` Gradle property
- Tools: Spotless + google-java-format, Error Prone + NullAway, SpotBugs,
  JaCoCo report and verification
- Tasks: `stlFmt`, `stlFmtCheck`, `stlLint`, `stlSec`, `stlCov`, `stlCheck`,
  `stlInfo`
- A Java 21 floor for both the consumer toolchain and the JVM the Gradle
  daemon runs on, each failing fast with a clear message
- TestKit functional tests across Gradle 9.0 and latest, consumer toolchains
  21 and 25, with the configuration cache on
- GitHub Actions CI, release-please, publishing to the Gradle Plugin Portal
- README covering installation, requirements, tasks, profiles, flags,
  settings, per-tool escape hatches and git-hook snippets

### google-java-format 2.0.0 notes

- **Spotless compatibility is confirmed.** Spotless 8.11.0 ships 2.0.0 as its
  default. Test 4 still asserts a 2.0.0 cleanup ran.
- **It runs inside the Gradle daemon**, so the daemon needs JDK 21 even when
  the project's toolchain is 21+. See the daemon JVM check below.
- **Cleanup is on by default.** Besides whitespace, it removes redundant
  semicolons, empty annotation parentheses and parentheses around a single
  untyped lambda parameter. Keep the default: `stlFmt` is allowed to change code.
- **Formatting differs from 1.x**, notably sole-argument lambdas stay on the
  call's line. A service adopting Sterling should reformat in one commit and add
  that SHA to `.git-blame-ignore-revs`. Say this in the README.

## Configuration model

### DSL

```kotlin
import dev.balakmran.sterling.Profile   // Kotlin DSL only; Groovy can use the full name

sterling {
    profile = Profile.STANDARD          // LENIENT | STANDARD | STRICT
    attachToCheck = true                // default from profile

    format { enabled = true }
    errorProne {
        enabled = true
        warningsAsErrors = false        // default from profile
        disable("UnusedVariable")       // check names; adds to Sterling's
    }
    nullAway { enabled = true }
    spotbugs {
        enabled = true
        excludeFilter = file("config/spotbugs-exclude.xml") // merged with Sterling's
    }
    coverage {
        enabled = true
        instruction = 80                // percent, 0..100
        branch = 70                     // percent, 0..100
        excludes.add("**/*Application*") // class-file patterns
    }
}
```

Types: `Property<Profile>`, `Property<Boolean>`, `Property<Int>`,
`SetProperty<String>` behind `disable(vararg String)`, `RegularFileProperty`,
`ListProperty<String>`. Each block is a nested object with an `Action`-taking
function, so the same syntax works from the Groovy DSL.

### Profile defaults

Every value uses `.convention(profile.map { ... })`, so an explicit consumer
value always wins.

| Setting | LENIENT | STANDARD | STRICT |
|---|---|---|---|
| `attachToCheck` (`check` depends on `stlCheck`) | false | true | true |
| `format.enabled` | true | true | true |
| `errorProne.enabled` | true | true | true |
| `errorProne.warningsAsErrors` | false | false | true |
| `nullAway.enabled` | true | true | true |
| `spotbugs.enabled` | false | true | true |
| `coverage.enabled` | false | true | true |
| `coverage.instruction` | 0 | 80 | 95 |
| `coverage.branch` | 0 | 70 | 85 |

- `format.enabled` is true in every profile; the flag exists so a consumer can
  turn it off explicitly.
- `nullAway.enabled` is true everywhere because NullAway only checks
  `@NullMarked` code: it does nothing until a package opts in.
- `LENIENT` turns off the gate's wiring to `check`, not compilation. Error Prone
  and NullAway findings at `ERROR` severity still fail `compileJava`.
- `warningsAsErrors` adds `-Werror`, which also fails on javac's
  default-on warnings such as `[removal]`. That is intended for `STRICT`.

### Choosing the profile without editing the build script

`profile`'s convention reads the `sterling.profile` Gradle property
(case-insensitive) and falls back to `STANDARD`. A project puts its default in
`gradle.properties` and CI overrides it on the command line:

```properties
sterling.profile=standard
```

```bash
./gradlew build -Psterling.profile=strict
```

A `profile = ...` in the build script still wins over the property, so a project
that wants CI to choose leaves it out of the script.

### Validation

Thresholds outside 0..100 and an unknown `sterling.profile` fail with a clear
message naming the setting and the allowed values. There is no `afterEvaluate`,
so validation runs when a value is read: when `jacocoTestCoverageVerification`
is configured and when `stlInfo` runs. A build that touches neither does not
validate.

### Three layers of configuration

1. **Profile** sets the defaults.
2. **Sterling's settings** (above) cover the common adjustments.
3. **The tool's own DSL** covers everything else: `spotless { }`,
   `options.errorprone { }` on `JavaCompile`, `tasks.spotbugsMain { }`,
   `jacoco { }`. Sterling applies the tools; it never hides them, and a
   consumer's configuration applies alongside Sterling's.

What keeps layer 3 working:

- Sterling sets tool values with `.convention(...)` where the tool exposes a
  `Property`. Where it doesn't (`jacoco.toolVersion`), Sterling sets the value
  when the plugin is applied, so the consumer's script, which runs later, wins.
- Sterling adds a tool's dependency only when the consumer has not declared
  that module in the same configuration. This also lets a consumer move to a
  newer tool version before a Sterling release; it works in 0.1 but is not yet
  supported or tested.

The README documents layer 3 per tool with an example. Conflict detection is
out of scope.

### Lazy flags — the core design rule

The consumer's `sterling { }` block is evaluated **after** Sterling is applied,
so a flag can never decide whether a third-party plugin gets applied (that would
need `afterEvaluate`, which is forbidden). Sterling always applies the
underlying plugins, and each flag controls behaviour through providers:

| Tool | How the flag is honoured |
|---|---|
| Spotless | `stlFmt` / `stlFmtCheck` depend on the Spotless tasks only when `format.enabled`; Spotless's `enforceCheck = false` so it never attaches itself to `check` |
| Error Prone | `options.errorprone.isEnabled` bound to `errorProne.enabled`. `error_prone_core` added to the `errorprone` configuration inside `withDependencies { }` only when enabled and not already declared, so nothing is resolved when it is off |
| NullAway | `nullaway` added in the same `withDependencies { }` only when both `errorProne.enabled` and `nullAway.enabled` are on. Under the same condition, `jspecify` is added to `compileOnly` and `testCompileOnly` in their `withDependencies { }`. Its check severity and options go into the Error Prone `checks` / `checkOptions` map properties via `putAll(provider)`, empty when off |
| SpotBugs | Apply `com.github.spotbugs-base`, **not** `com.github.spotbugs`. The base plugin creates no tasks and does not attach to `check`; Sterling registers `spotbugsMain` itself and wires it only when enabled |
| JaCoCo | Core plugin, always applied. The JaCoCo agent on every `Test` task is enabled only when `coverage.enabled` (JaCoCo turns it on for all of them by default); `jacocoTestReport` finalizes `test` only when enabled, and is `onlyIf` the flag; `jacocoTestCoverageVerification` is wired into `stlCov` only when enabled. Coverage off means no agent, no `.exec` file and no report, so a JDK that JaCoCo doesn't support yet can't break tests |

Wire conditional task dependencies (`dependsOn`, `finalizedBy`) through
`Flags.whenOn`, which returns `providers.provider { if (flag.get()) tasks else
emptyList() }` holding `TaskProvider`s. Not `flag.map { ... }`: Gradle takes a
mapped provider's dependencies from the flag's producers, so the tasks in its
value get dropped whenever something else realises the graph first (`./gradlew
test stlCov` ran no verification). Task names in a provider don't resolve
either. Or use `onlyIf` on a captured `Provider<Boolean>`, never a captured
extension.
Compiler flags that depend on a setting (`-Werror`) go through a
`CommandLineArgumentProvider` with an `@Input` property, so they count as task
inputs.

JaCoCo details:

- `JacocoLimit.minimum` is a `BigDecimal`, and the agent's `enabled` is a plain
  boolean, not `Property`s. Set them inside the
  `tasks.named("jacocoTestCoverageVerification") { }` and
  `tasks.named<Test>("test") { }` configuration actions. Those run after the
  consumer's build script, so they see the consumer's values and stay
  configuration-cache safe.
- If something realises one of those tasks while the build script is still
  being evaluated, the action runs before `sterling { }` and captures the
  defaults. Test 17 catches this.
- Don't move the limits into `doFirst`. That changes the inputs after they are
  fingerprinted, so a raised threshold could come back `UP_TO_DATE`.
- Use `INSTRUCTION` and `BRANCH` counters with `COVEREDRATIO`, converting
  percent to a ratio.
- Apply `coverage.excludes` identically to the `classDirectories` of
  `jacocoTestReport` and `jacocoTestCoverageVerification`.
- JaCoCo already skips classes and methods carrying an annotation whose simple
  name contains `Generated` with `CLASS` or `RUNTIME` retention (Lombok's
  `@Generated`, or a project's own). It's the Java counterpart of
  `# pragma: no cover`; document it in the README. MapStruct's and
  `jakarta.annotation.Generated` have `SOURCE` retention and need `excludes`.

## Behaviour spec

### Base plugin — `dev.balakmran.sterling`

1. Applies Gradle's `base` plugin, so a `check` lifecycle task exists.
2. Creates the `sterling` extension and the `Profile` enum.
3. Registers lifecycle tasks, all `group = "sterling"`, none with actions of
   their own:

   | Task | Purpose | Aggregates (when enabled) |
   |---|---|---|
   | `stlFmt` | Format sources (changes code) | `spotlessApply` |
   | `stlFmtCheck` | Verify formatting | `spotlessCheck` |
   | `stlLint` | Compile-time analysis | `compileJava`, `compileTestJava` (Error Prone and NullAway run inside them) |
   | `stlSec` | Bytecode analysis | `spotbugsMain` |
   | `stlCov` | Coverage verification | `jacocoTestCoverageVerification` |
   | `stlCheck` | The gate | `stlFmtCheck`, `stlLint`, `stlSec`, `stlCov` |

4. Wires `check` to `stlCheck` lazily from `attachToCheck`. `stlCheck` still
   runs when invoked directly.
5. Registers `stlInfo`, which prints the resolved configuration:

   ```
   Sterling 0.1.0
   Profile:              STANDARD
   Gate wired to check:  yes
   Daemon JVM:           25
   Java toolchain:       25
   Formatting:           on   (google-java-format 2.0.0)
   Error Prone:          on   (2.52.0; warnings are not errors; 1 check disabled)
   NullAway:             on   (0.14.3; JSpecify 1.0.1; @NullMarked code only)
   SpotBugs:             on   (4.10.5; consumer filter merged)
   Coverage:             on   (instruction >= 80%, branch >= 70%; 1 exclude)
   ```

   - Version strings come from `versions.properties`, generated at build time
     from the version catalog, not hardcoded.
   - The `Java toolchain` line shows `not active (...)` with the reason: the
     Java plugin or `java` not applied. Tool lines still show their settings.
   - Shows `off (Error Prone off)` for NullAway when Error Prone is disabled.
   - Prints at quiet log level, so `-q` still shows it. ASCII `>=`, so
     consoles without UTF-8 render it.
   - A custom task class whose inputs are properties wired from providers;
     configuration-cache safe; never up to date (`@UntrackedTask`).

### Java plugin — `dev.balakmran.sterling.java`

1. **Daemon JVM check.** At apply time, before anything else, fails when
   `JavaVersion.current()` is below 21, regardless of flags:
   `Sterling requires Gradle to run on JDK 21+ (found 17). Run ./gradlew updateDaemonJvm --jvm-version=21, or point JAVA_HOME at JDK 21+.`
2. Applies the base plugin, so the extension, the `stl*` tasks and `stlInfo`
   always exist. Applies Spotless, `net.ltgt.errorprone`,
   `com.github.spotbugs-base` and `jacoco` inside
   `pluginManager.withPlugin("java") { }`. Without `java`, the tools stay off
   and nothing fails. Applying Sterling before `java` works the same as after.
3. **Toolchain check.** Registers an internal `stlToolchainCheck` task that
   `compileJava` depends on. Its input is the compiler's language version, read
   lazily from `JavaCompile.javaCompiler`. Below 21 it fails with:
   `Sterling requires a Java 21+ toolchain (found 17). Set java.toolchain.languageVersion to 21 or later.`
   On success it writes `build/sterling/toolchain-check.txt`, so it's
   `UP_TO_DATE` until the toolchain changes.
4. **Spotless:** `java { googleJavaFormat(<pinned>); formatAnnotations(); targetExclude("**/build/generated/**") }`
   over every source set; `enforceCheck = false`.
   - No `removeUnusedImports()`: the google-java-format step already does it,
     and the separate step would resolve Spotless's default version, not the pin.
   - Spotless formats every source set by default, which includes Spring AOT's
     `build/generated/aotSources`, hence the exclusion.
   - Spotless resolves google-java-format from the consumer's repositories when
     the task graph is built, so a consumer needs `mavenCentral()`. The same
     goes for Error Prone, NullAway, JSpecify and SpotBugs.
5. **Error Prone:**
   - `-XDaddTypeAnnotationsToSymbol=true` on every `JavaCompile`. Error Prone
     requires it on JDK 21 since 2.46.0, and NullAway's JSpecify mode depends on
     the same javac fix
   - `disableWarningsInGeneratedCode = true`
   - `excludedPaths` set to the regex `.*[/\\]build[/\\]generated[/\\].*`
     (in Java source, escape each backslash). It's separator-agnostic, so it matches
     on Windows too. Covers annotation processors (Lombok,
     MapStruct), OpenAPI generators and Spring AOT's `build/generated/aotSources`.
     A unit test checks both separators, since CI is Ubuntu-only
   - Default checks, plus `errorProne.disable(...)` mapped to `OFF` in `checks`
   - `-Werror` when `errorProne.warningsAsErrors`
6. **NullAway:**
   - `com.uber.nullaway:nullaway` in the `errorprone` configuration
   - `NullAway` at `ERROR` severity
   - `NullAway:OnlyNullMarked=true`: only code under `@NullMarked` is checked,
     so adopting is per package via `package-info.java`
   - `NullAway:JSpecifyMode=true`
   - `org.jspecify:jspecify` on `compileOnly` and `testCompileOnly`, so
     `@NullMarked` and `@Nullable` work without a consumer dependency.
     - `compileOnly` keeps it off the runtime classpath. Spring Boot 4 apps
       already get it through `spring-core`; the higher version wins.
     - Libraries that annotate public API should still declare it as `api`,
       so Kotlin and other downstream consumers see the annotations.
     - With NullAway off, Sterling doesn't add it; code that keeps using the
       annotations declares the dependency itself.
7. **SpotBugs:**
   - Registers `spotbugsMain` only (tests are not analysed by default), with
     HTML, XML and SARIF reports.
   - Sterling's default exclude filter ships as a plugin resource. It covers
     generated sources and three patterns that Spring constructor injection
     and records trigger across ordinary code: `EI_EXPOSE_REP`,
     `EI_EXPOSE_REP2` and `CT_CONSTRUCTOR_THROW`.
   - An internal `stlSpotbugsFilter` task writes the filter
     `spotbugsMain` uses to `build/sterling/spotbugs-exclude.xml`. It merges the
     `<Match>` elements of Sterling's resource and of `spotbugs.excludeFilter`
     when set. The resource text is an `@Input` read at configuration time, the
     consumer file an optional `@InputFile`, the result an `@OutputFile`.
8. **JaCoCo:**
   - The agent on every `Test` task follows `coverage.enabled`.
   - `jacocoTestReport` finalizes `test` when enabled, with HTML and XML reports.
   - Both JaCoCo tasks `dependsOn("test")`: Gradle's JaCoCo plugin doesn't add
     it, and without it they skip for lack of data.
   - `jacocoTestCoverageVerification` uses the `coverage` thresholds.
   - `coverage.excludes` applies to both.
9. Consumer configuration of any of these tools applies alongside Sterling's
   (see "Three layers of configuration").

## Testing

Functional tests (JUnit 5 + TestKit) in a `functionalTest` JVM test suite.

- **Matrix.** Each case runs on every combination of Gradle {9.0, latest} and
  consumer toolchain {21, 25}, unless the case pins its own. CI may split the
  combinations into parallel jobs.
- **Flags.** Every run uses `--configuration-cache` and
  `--configuration-cache-problems=fail`. On the latest Gradle it also uses
  `--warning-mode=fail`, to catch Gradle 10 deprecations early. If a
  third-party plugin emits one, record it here and suppress it for that case
  rather than dropping the flag.
- **JDKs.** The `functionalTest` task resolves each JDK a fixture needs through
  Gradle's toolchain service and passes its path as `sterling.jdk<n>`. On CI,
  `org.gradle.java.installations.fromEnv` finds the `JAVA_HOME_<n>_X64` JDKs
  setup-java installs; locally, Gradle finds installed JDKs (SDKMAN included).
  Sterling's build never downloads a JDK: a missing one fails with Gradle's
  toolchain error. Fixtures list those paths in
  `org.gradle.java.installations.paths` with auto-detect and auto-download
  off, so a consumer build only sees the JDK the case intends.

## CI and release

- **`ci.yml`** on push and pull request:
  - `permissions: contents: read`; checkout with `persist-credentials: false`.
  - Actions pinned by commit SHA with a version comment.
  - A newer push to the same pull request cancels the older run.
  - JDK 17, 21 and 25 installed; build with 21; `gradle/actions/setup-gradle`.
  - `./gradlew build functionalTest --warning-mode=fail`. Ubuntu only.
- **Dependabot** for the `gradle` (version catalog) and `github-actions`
  ecosystems, weekly. It doesn't update `gradle/verification-metadata.xml`,
  so its Gradle PRs need the checksums regenerated before they pass.
- **release-please** with `release-type: simple`:
  - `bump-minor-pre-major: true`, so a breaking change bumps the minor before
    1.0.
  - `initial-version: 0.1.0`.
  - The version lives in `version.txt`, which the build reads.
  - `extra-files` with `x-release-please-start-version` / `x-release-please-end`
    markers updates the README install snippet.
- **Publishing** runs in the release-please workflow, as a job gated on
  `steps.release.outputs.release_created`: `./gradlew publishPlugins` with the
  `GRADLE_PUBLISH_KEY` and `GRADLE_PUBLISH_SECRET` repo secrets. A separate
  workflow on `release: published` would never fire, because a release created
  with `GITHUB_TOKEN` doesn't start other workflows.
- Plugin metadata: `website` and `vcsUrl` point to `github.com/balakmran/sterling`;
  `displayName`, `description` and `tags` on both plugin IDs.
- The first Plugin Portal submission is manually reviewed; expect a delay before
  0.1.0 resolves publicly. IDs under a custom domain are checked against its
  ownership, so have balakmran.dev ready to verify.
